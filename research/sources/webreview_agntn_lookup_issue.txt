What's missing?

puzzles_list with an address answers 0 matching puzzles: (none) when the other filters rule the puzzle out, which reads exactly like "this address isn't in the catalog". On OMP that's the common case, not an edge: OMP sends every parameter in the schema, so an address lookup always carries some collection, status and withPubkey. On 2026-09-26 six OMP sessions made about 35 address lookups this way. The agents' own labels were things like "Searching entire catalog for exact reward address" and "Resolving target without catalog status filters", while the call itself pinned collection: "ktimesg" and status: "unsolved". A few gave up and tried collection: "none" or "any".
Steps to reproduce

import { listTool } from "./src/tool-operations.ts";

const address = "1crypto24HCr178iMcKd5iUi5D4rsg1nK"; // zden/level-halv

await listTool({ address });
await listTool({ address, collection: "b1000", chain: "bitcoin", status: "unsolved", withPubkey: false });
await listTool({ address, collection: "zden", chain: "bitcoin", status: "solved", withPubkey: false });
Expected

When an address matches a puzzle that the filters exclude, the answer says so, for example 0 matching puzzles. 1crypto24H... is zden/level-halv (unsolved), outside collection b1000.
Actual

1 matching puzzles: zden/level-halv unsolved 0.003125 BTC 1crypto24HCr178iMcKd5iUi5D4rsg1nK
0 matching puzzles: (none)
0 matching puzzles: (none)

Proposed fix

An address is close to a unique key, so an empty filtered result can look the address up once without filters and name what it found and which filter dropped it. That covers every surface, not just OMP. Accepting a blank collection from OMP as "no filter" would help too, but #272 went the other way for good reasons, and the hint above makes the choice matter less.
Notes

agntn/sessions#152 is the same OMP behavior hitting sessions_list.

Checked against ee051c9 (0.24.0).
